# Story — More ways to pay: VietQR transfer and MoMo

Module: `payments` · Plan item 12 (P3) · Requirements: PAY-020, PAY-021, PAY-022 (`docs/payments/SRS.md` §4.2), and the changes they make to ORD-006 and ORD-007 item 8 (`docs/orders/SRS.md`), ADMIN-016 item 4 with AC-11 and AC-12 (`docs/admin/SRS.md`) and SITE-006 item 3 (`docs/site/SRS.md`)
Design system: `design/design-system.md` (§2.1.5 outline pill, §2.1.6 filled pill, §2.1.17 radio row, §2.1.28 icon, §2.2.3 button) · Architecture: `docs/architecture/overview.md`, `services.md` (§3.5 payment options, §3.10 `POST /v1/orders`, §3.11 `GET /v1/orders/{id}`, §3.13 `POST /v1/orders/{id}/payment`, §3.15 `PUT /v1/orders/{id}`, §3.17 the VNPay notice), `erd.md` (§3.7 `payment_methods`, §3.12 `orders`, §3.16 `payment_attempts`, §3.17 `payment_notices`)

> Owner decision that shapes this story: the owner chose **online payment only** — there is no cash on delivery, and until this story checkout offers **VNPay only**. This story adds **VietQR bank transfer** and the **MoMo wallet** as two more *online* ways to pay beside VNPay, each offered only when the owner has supplied what it needs. It stays P3: the shop opens without it, and nothing in the shop breaks while the settings are absent — a way to pay that is not set up is simply not listed.

## 1. User story

As a **customer** (a guest holding the order's token in this browser, or a signed-in customer), I want to pay by scanning a QR code with my banking app, or with my MoMo wallet, as well as on VNPay's page, so that I can pay the way I already pay and the shop confirms my order without my using a card.

Other actors this story touches:

- **Dealer** (owner or staff, signed in) — marks a **bank-transfer** order paid on the order's admin page once the money has landed. This is the one case where a person marks an order paid, and it is a bank-transfer order and no other.
- **MoMo** (the wallet provider) — calls the shop's MoMo notice address from its own servers; the signature is the only thing that proves who is calling.
- **Owner** — supplies MoMo's three keys and the shop's own bank account (bank, account number, holder), and registers the MoMo notice address. Everything is already requested in the console with this plan (`request_secret` ×7: `MOMO_PARTNER_CODE`, `MOMO_ACCESS_KEY`, `MOMO_SECRET_KEY`, `VIETQR_BANK_BIN`, `VIETQR_BANK_NAME`, `VIETQR_ACCOUNT_NUMBER`, `VIETQR_ACCOUNT_NAME`; `request_setup` ×1: the MoMo notice address `/api/v1/payments/momo/ipn`).
- **Stranger** — anyone who is not the order's customer, the dealer or MoMo learns nothing about an order and changes nothing.

## 2. What exists today, and where this story plugs in

Read from `main`, not assumed:

- **The payment seam** (`internal/orders`): the code list `offered = ["vnpay"]`, a `Providers` map keyed by way-to-pay id (`server.go` registers `vnpay` only), `GET /v1/payment-options` listing `offered` with `is_available` taken from the provider, `POST /v1/orders` refusing a way not in `offered` (422) and answering 503 when its provider is registered and unavailable, and `CheckPayable`, which answers 409 for a way not in `offered`.
- **`internal/payments`** holds VNPay alone: `thirtyMinuteWays = ["vnpay"]` for the 30-minute rule, the notice at `GET /v1/payments/vnpay/ipn`, `payment_attempts` (its `provider` check already allows `momo`) and `payment_notices` (its success check is written in VNPay's codes, `00` and `00`).
- **The pages name VNPay in code.** `Checkout.tsx` finds `vnpay` in the options and draws one fixed row; `lib/orders.ts` types the placing request's `payment` as the literal `"vnpay"`; `Product.tsx` reads the `vnpay` record alone for "Payment options"; the order page's `canPay` shows "Pay now" for **any** unpaid, not cancelled order; `PaymentReturn` reads VNPay's `vnp_TxnRef` and `vnp_ResponseCode`, and its words name VNPay.
- **The dealer's side** (plan item 17, "Dealer handles orders", in verification as PR #88): `PUT /v1/orders/{id}` refuses every `paid` with 422 "Only the payment provider marks this order paid." whatever the way to pay, and the admin order page shows "Paid" or "Awaiting payment" and "VNPay transaction <number>" read-only.
- **The records.** `payment_methods` already holds `bank` ("Bank transfer (VietQR)", note "Scan the QR code on the next screen with any banking app. We send the pair as soon as the money lands.") and `momo` ("MoMo wallet", note "Confirm the payment in the MoMo app; the order is marked paid at once."). What is *offered* is code plus the owner's settings, never data (`erd.md` §3.7).

This story **registers two more ways to pay behind that seam** and makes the pages that named VNPay in code draw what the shop says it can complete.

## 3. Decisions this story makes (so no later stage guesses)

1. **PAY-022 AC-3 cannot hold as written, so the SRS is amended with this story.** It says the story edits no file of the Checkout page; but `Checkout.tsx`, `lib/orders.ts` and `Product.tsx` name VNPay alone, so a third row can only appear if they stop. The story edits those pages **only where they named VNPay or "Pay now"**; no page holds a list of ways to pay afterwards. `docs/payments/SRS.md` PAY-022 item 2 and AC-3, PAY-020 item 4 and `docs/orders/SRS.md` ORD-007 item 8 are amended in the same pull request as this file.
2. **A button that can only fail is not drawn.** "Pay now" answers 409 for a bank-transfer order (PAY-020 item 4), so the order page draws the QR block *instead of* "Pay now" for an unpaid bank-transfer order. VNPay and MoMo orders keep "Pay now".
3. **An unavailable way does not block the others.** Only VNPay can be listed and unavailable (keys missing). That row is drawn with the alert line, cannot be chosen, and the first available way is selected; "Place order" is disabled only when no listed way is available (so the VNPay story's behaviour with VNPay alone is unchanged).
4. **Marking a bank order paid does what VNPay's notice does.** It goes through the same one function that sets `paid` (`orders.MarkPaid`), so an order still at "placed" becomes "confirmed" in the same step, and an order already cancelled is marked paid and stays cancelled so the dealer sees it and refunds it (PAY-002 items 4 and 9; PAY-020 conflict row). Marking an already-paid bank order paid again is not an error and changes nothing; marking anything unpaid is always refused.
5. **The two time rules skip the 14 sample orders** (`DOI-24804` to `DOI-24817`), the 24-hour rule as well as the 30-minute one, so the dashboard's figures hold (PAY-003 item 4, SRS open question 7). Both rules leave shipped and delivered orders alone.
6. **The QR is drawn by the shop itself.** No third-party QR or image service is called, so the shop's bank details reach no one but the customer who placed the order. The code follows the VietQR (NAPAS 247) payload that Vietnamese banking apps read. Which library draws it, and whether the browser or the backend draws it, is TL's decision in the technical design; `package.json` and `go.mod` are changed by TL's tools, not by hand.
7. **The bank account is never public.** Its holder, bank, number and the QR payload are served only by the order's own transfer-details call, to the holder of the order's token (or the linked customer); not by `GET /v1/payment-options`, not by the public order read, not by any collection.
8. **MoMo's notice** is `POST /v1/payments/momo/ipn` (public path `/api/v1/payments/momo/ipn`, the address already declared in the console). It answers **204** when it accepted the notice or had already processed it (what MoMo requires), **400** when it refused it (bad signature, a partner code that is not the shop's, an unknown reference, a wrong amount, an unreadable body), and **5xx** when the database failed so MoMo sends it again. TL confirms the codes against MoMo's current documentation.
9. **Which provider's words the result page uses comes from the shop's answer** (the order's way to pay), never from the address the browser arrived with. The page still never decides a result from the address (PAY-004 item 1).
10. **No hard-coded words for a provider.** The page's MoMo wording is new content keys the owner can edit in the Studio; the VNPay wording is unchanged.

## 4. In scope

**Backend (Go, PostgreSQL)**

- **Settings** read once from the environment, none required to start: `MOMO_PARTNER_CODE`, `MOMO_ACCESS_KEY`, `MOMO_SECRET_KEY` (secrets; the secret key and access key never leave the server), `MOMO_API_URL` (optional; MoMo's sandbox is the default and going live changes this value, not code), and the bank account `VIETQR_BANK_BIN`, `VIETQR_BANK_NAME`, `VIETQR_ACCOUNT_NUMBER`, `VIETQR_ACCOUNT_NAME`. All named in `.env.example` with no value.
- **What is offered**: the ordered list of ways to pay becomes `vnpay`, then `bank` when all four bank values are set, then `momo` when all three MoMo keys are set. `GET /v1/payment-options`, the 422 for a way not offered, the 503 gate and "Pay now"'s state check all follow it.
- **Bank transfer**: a provider with no payment address (placing answers `payment_url: ""`); the transfer-details call for an order (proposed `GET /v1/orders/{id}/transfer`, TL fixes the name) with the same access as "Pay now"; the 24-hour rule in the same in-process check that already runs every 30 seconds.
- **Dealer marks a bank order paid**: `PUT /v1/orders/{id}` accepts `{"paid": true}` for a bank-transfer order and keeps refusing every other `paid` (ADMIN-016 AC-11, AC-12), through `orders.MarkPaid` under the order's row lock.
- **MoMo**: a provider whose payment address is created by a call to MoMo's create-payment API (signed with HMAC-SHA256, amount read from the database, a reference different for every attempt, the shop's `/payment/return` and the MoMo notice address in the request, a 3-second limit as for any provider), its notice at `POST /v1/payments/momo/ipn`, and `momo` added to the 30-minute rule. Each attempt is a `payment_attempts` row; each notice a `payment_notices` row.
- **Migrations** (TL's design names them): the success check of `payment_notices` is generalised so MoMo's success code is accepted (it is written in VNPay's `00`/`00` today); the `momo` record's note loses "the order is marked paid at once" (SITE-016 item 5, PAY-021). Never an edit to a merged file.
- **The dealer's reads** carry MoMo's transaction number in the same `transaction_no` field VNPay's uses.

**Frontend (Vite + React + Tailwind tokens)**

- `Checkout.tsx` step 03 draws one radio row for each way `GET /v1/payment-options` lists, the first available one selected; `lib/orders.ts` sends the chosen way (no literal `"vnpay"`); the summary names it.
- `Product.tsx`'s "Payment options" lists the same ways.
- The order page draws the **bank-transfer block** (new component under `src/components/`, one mount in the existing order page parts) and no "Pay now" for an unpaid bank-transfer order.
- `PaymentReturn` reads MoMo's return address as well as VNPay's and says "MoMo" where it says "VNPay" for a MoMo order.
- The dealer's order page gets a **"Mark as paid"** button for an unpaid bank-transfer order and reads "MoMo transaction <number>" for a MoMo order.
- A client file `src/lib/more-ways-to-pay-vietqr-transfer-and-momo.ts` on `src/lib/api.ts` (transfer details, "Mark as paid"); no second API client.

## 7. Acceptance criteria

Each criterion names the SRS requirement and criterion it narrows (`SC-n [REQ AC-m]`). Test writes at least one case per `SC`; TL's reviews count this list. "Shop" means the running API. Amounts are VND with `vi-VN` formatting on the shop's pages (`3.140.000 ₫`); MoMo's unit is whole VND (`3140000`), not ×100 as VNPay's is.

How the cases are driven (so a case is not reported green for something it could not observe):

- **Settings are a precondition of the run.** Without the bank account every bank criterion that needs the way listed is **UNVERIFIED** (instrument missing: the four `VIETQR_*` values); without the three MoMo keys every MoMo criterion that needs a built request or a verified notice is UNVERIFIED (instrument: `MOMO_PARTNER_CODE`, `MOMO_ACCESS_KEY`, `MOMO_SECRET_KEY`). The "not configured" criteria (SC-2, SC-3, the refusals) are observed with the settings absent.
- MoMo's servers cannot reach a deployment on a `.localhost` address, and a run may have no route to MoMo's sandbox. Where MoMo would be called, the case points `MOMO_API_URL` at a stand-in that answers as MoMo's create-payment API does, and where MoMo would call the shop the case sends **the same request MoMo sends**, signed with the shop's secret key by the same algorithm. A case that needs MoMo's real sandbox page is marked so and is fully observed only with a public address.
- The dealer's moves and times are set directly in the test database where a case needs them (an order's status, its placed time — 25 hours, 31 minutes, 2 hours old — and `is_sample`), as the VNPay story's cases do.

Choosing another row selects it alone (by click and by keyboard) and the summary names the chosen way.
- **SC-2 [PAY-022 AC-2; PAY-020 AC-2; PAY-021 AC-2; ORD-006 AC-3, item 3]** (BE + UI): With the bank account set and MoMo's keys not, the options and the rows are VNPay then bank transfer, with no MoMo; with MoMo's keys set and no bank account, VNPay then MoMo; with neither, VNPay alone — one row, selected — exactly as the VNPay story left it. ### B. Placing and paying by each way (PAY-020 item 2, PAY-021 item 2, ORD-006 items 4–5, ORD-007 items 8–9)

- **SC-5 [PAY-020 item 2; ORD-006 items 4–5, AC-9]** (BE + UI): With Bank transfer chosen, `POST /v1/orders` answers 201 with `payment_url: ""`, an unpaid order at status "placed", the pairs set aside and the order's token; the bag is emptied and the browser goes to `/orders/<id>?placed=1`, where the QR block is shown. No VNPay or MoMo attempt is stored. This works while VNPay's keys are missing.
- **SC-6 [PAY-021 item 2; ORD-006 AC-7]** (BE + UI): With MoMo chosen and its keys set, `POST /v1/orders` answers 201 with a non-empty `payment_url` that MoMo's create-payment answer gave, and one `payment_attempts` row for provider `momo`; the bag is emptied and the browser goes to that address. The amount in the request to MoMo equals the Total shown at checkout, in whole VND.
- **SC-7 [PAY-021 AC-3, items 2–3]** (BE): For an unpaid MoMo order of 3.140.000 ₫, the request the shop sends to MoMo carries the shop's partner code; the amount `3140000` from the database (an amount in the placing request or on "Pay now" changes nothing); a reference holding the order number (`DOI-24818-1`), at most 100 characters, different for every attempt (`DOI-24818-2`) — two asked at the same moment never share one; the shop's `/payment/return` as the return address; the shop's MoMo notice address; and a signature (HMAC-SHA256 with the shop's secret key) that verifies with that key and not with another. The secret key appears nowhere in the request. A signed success notice for the **first** reference still finds the order and pays it.
- **SC-8 [PAY-021 item 2; ORD-006 AC-8, item 5; ORD-007 failure row]** (BE + UI): When MoMo gives no address at placing — unreachable, slower than the provider's 3 seconds, or it refuses (for example an amount above its limit) — the order still exists, unpaid, at "placed", its pairs taken; `payment_url` is `""`; the browser goes to `/orders/<id>?placed=1`, where "Pay now" is shown. If "Pay now" cannot get an address either, the page stays, shows "We could not open the payment page. Please try again." under the button and enables it again.
- **SC-9 [PAY-001 item 7; ORD-007 AC-14, AC-17 to AC-20; PAY-021 item 2]** (BE + UI): "Pay now" with the token on an unpaid, not cancelled MoMo order inside its 30 minutes answers 200 with a fresh MoMo address (a new attempt, a new reference) and the order page sends the browser there, the button disabled while it waits. For a paid order, a cancelled order and an order whose 30 minutes are over it answers 409 `conflict` (three different sentences, as the VNPay story has them); with no token, another order's token or an unknown id it is the one 404 body; with MoMo's keys unset it answers 503 `payment_unavailable` after the 404 and 409 checks.
- **SC-10 [PAY-020 item 4, AC-6; ORD-007 item 8]** (BE + UI): "Pay now" with the token on an unpaid, not cancelled bank-transfer order answers 409 `conflict` with a sentence saying the order is paid by bank transfer, and stores nothing; for a paid or a cancelled bank-transfer order it answers 409 as for any order, and with no token 404. The order page draws **no** "Pay now" for an unpaid bank-transfer order (the QR block is in its place) and still draws it for an unpaid VNPay or MoMo order.

### C. The bank-transfer QR code (PAY-020)

- **SC-11 [PAY-020 AC-3, item 2]** (UI + BE): For an unpaid, not cancelled bank-transfer order of 3.140.000 ₫, `/orders/<id>` with its token — straight after placing (`?placed=1`), later, and after a refresh — shows the QR code and, written as text for typing by hand, the account holder, the bank, the account number, `3.140.000 ₫` and the order's number as the transfer note, with the line "Scan this QR code with any banking app. We send the pair as soon as the money lands." Every value is the shop's setting or the stored total.
- **SC-12 [PAY-020 AC-4]** (BE + UI): Decoding the QR code shown (or the payload the shop serves for it) gives a VietQR payload that banking apps read: it names the shop's bank BIN and account number, the amount `3140000`, and the order number as the note, and its checksum is valid. The amount is read from the database; one sent by the browser is ignored. No request for the QR or its picture leaves the shop's own origin.
- **SC-13 [PAY-020 AC-9, permission row; ORD-008]** (BE): The transfer-details call answers 200 with `Cache-Control: no-store` and exactly the holder, bank, account number, amount, note and QR payload to the order's token (or the linked customer's session). With no token, another order's token, a dealer session without the token, or an unknown id it answers the one same 404 body. With a valid token for a paid order, a cancelled order or an order that is not bank transfer it answers 409. With the account no longer set it answers 503 `payment_unavailable`. The answer carries no phone, email, address or note of the order, and no other call of the shop (options, the public order read, the `payments` collection) carries the account.
- **SC-14 [PAY-020 AC-5, item 4; ORD-007 AC-6, AC-11]** (UI + BE): After the dealer marks a bank-transfer order paid, reopening `/orders/<id>` shows "Payment" as `Bank transfer (VietQR) · paid`, the heading "Your order is confirmed.", no QR block and no "Pay now". A bank-transfer order cancelled (by the dealer or by the 24-hour rule) shows the cancelled view and no QR block.
- **SC-15 [PAY-020 failure rows; story §6]** (UI): While the transfer details are being read, the rest of the order page is drawn and the block is a quiet `aria-busy="true"` placeholder of the QR's size, never the not-found view.
